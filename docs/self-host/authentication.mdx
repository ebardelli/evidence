A self-hosted Evidence deployment ([`evidence serve`](/cli/commands#evidence-serve)) includes a single built-in access control: shared [HTTP Basic Auth](/self-host#authentication) (`EVIDENCE_BASIC_USER` / `EVIDENCE_BASIC_PASSWORD`), or unauthenticated access on a trusted private network (`EVIDENCE_AUTH_DISABLED=true`). It does not provide user accounts, single sign-on, or an identity store of its own.

To authenticate users against your organization's identity provider, deploy `evidence serve` behind an authenticating reverse proxy (also known as an identity-aware proxy). The proxy integrates with your identity provider over OIDC or SAML, enforces sign-in on every request, and forwards only authenticated traffic to Evidence.

<Warning>
  Authentication controls who can reach the deployment; by default it does not scope what each user sees. Every authenticated user is served the same reports, queried against the single warehouse identity defined in [`connection.yaml`](/cli/connections). Upstream self-hosted deployments do not enforce per-report [access control](/features/page-level-access-control) or [row-level security](/features/access-rules) — those are applied against a per-viewer identity available only in [Evidence Studio](/self-host#self-host-vs-evidence-studio). This deployment's fork adds one narrow exception, a page-visibility allowlist described in [Restricting individual pages to an allowlist](#restricting-individual-pages-to-an-allowlist) below — it does not scope query results, so it is still not a substitute for Studio. Deployments that need real per-viewer report or row scoping should use Evidence Studio.
</Warning>

## Architecture

```
User ──▶ Authenticating reverse proxy (OIDC / SAML) ──▶ evidence serve
```

The proxy is the sole entry point and the authentication boundary; Evidence runs with its built-in authentication disabled. Evidence can optionally display the authenticated user's email in the sidebar (see [Displaying the proxy identity](#displaying-the-proxy-identity) below), but this is cosmetic — reports, queries, and filters remain the same for every authenticated user.

<Steps>
  <Step title="Restrict network access to the proxy">
    Deploy `evidence serve` on a private network or internal port that is not publicly routable, so the proxy is the only path to the application. A directly reachable deployment with authentication disabled is unprotected.
  </Step>
  <Step title="Disable built-in authentication">
    Set `EVIDENCE_AUTH_DISABLED=true` so Evidence treats the proxy as the authentication boundary. HTTP Basic Auth may be retained as an additional layer where required.
  </Step>
  <Step title="Configure the proxy against your identity provider">
    Connect the proxy to your identity provider over OIDC or SAML, and scope access to the appropriate users, groups, or domains. Route the proxy to the Evidence deployment.
  </Step>
</Steps>

## Displaying the proxy identity

Most authenticating proxies forward the signed-in user's identity to the upstream app as request headers — for example oauth2-proxy's `X-Auth-Request-Email`. Evidence can show that identity in the sidebar, in place of the default "Not logged in" state:

| Env Var | Purpose |
| --- | --- |
| `EVIDENCE_AUTH_PROXY_EMAIL_HEADER` | Name of the inbound header holding the viewer's email (e.g. `X-Auth-Request-Email`) |
| `EVIDENCE_AUTH_PROXY_NAME_HEADER` | Optional: name of the inbound header holding a display name (e.g. `X-Auth-Request-User`) |

<Warning>
  This is purely cosmetic — it only changes what the sidebar displays. It does not authenticate anyone, and it does not scope queries, filters, or reports per user. Only set `EVIDENCE_AUTH_PROXY_EMAIL_HEADER` when Evidence is reachable exclusively through the proxy (see [Restrict network access to the proxy](#architecture) above) — otherwise a request that reaches Evidence directly can set the header itself and impersonate any identity in the sidebar.
</Warning>

## Restricting individual pages to an allowlist

<Warning>
  This is a local extension on this deployment's fork of Evidence — it is not part of upstream Evidence and will not appear in other Evidence deployments. It is **not** a substitute for [Evidence Studio's](/self-host#self-host-vs-evidence-studio) per-viewer [page-level access control](/features/page-level-access-control) or [row-level security](/features/access-rules): those apply against a verified per-viewer identity and can scope both which reports a viewer sees and which rows they see within a report. This extension only compares the proxy-forwarded email header against an allowlist — it inherits the same trust assumptions as [Displaying the proxy identity](#displaying-the-proxy-identity) above (the header must not be spoofable, so Evidence must be reachable exclusively through the proxy), and it does **not** scope query results — every allowed viewer sees the same data. Deployments that need real per-viewer report or row scoping should use Evidence Studio.
</Warning>

A page can be gated to a specific set of viewer emails with an `auth:` block in its frontmatter, checked against the same proxy-forwarded identity used for the sidebar:

```md
---
title: Finance summary
auth:
  users: [alice@example.com, bob@example.com]
---
```

Add `query` to also allow anyone returned by a SQL query (run server-side against `connection.yaml`; the first result column is read as the allowed emails). `users` and `query` are additive — a viewer is allowed if their email appears in either:

```md
---
auth:
  users: [alice@example.com]
  query: select email from allowed_users where page = 'finance'
---
```

| Field | Purpose |
| --- | --- |
| `auth.users` | Static list of allowed emails. |
| `auth.query` | SQL query whose first result column is read as allowed emails. Cached for 60 seconds per query. |
| `auth.message` | Custom message shown to a denied viewer, in place of the default "does not have access" text. `{email}` is replaced with the viewer's email. |

If the frontmatter block is absent, the page is unrestricted (unchanged from default behavior). If it's present, a request without a proxy identity (no `EVIDENCE_AUTH_PROXY_EMAIL_HEADER` configured, or the header missing/blank) is refused with a 403, as is a viewer whose email matches neither list. This check only runs in `evidence serve`; in `evidence dev` there is no proxy identity to check against, so pages render normally for local authoring.

Use `auth.message` to tell a denied viewer how to get access, instead of the generic default:

```md
---
auth:
  users: [alice@example.com]
  message: "{email} isn't on the Finance team. Ask in #finance-access for a share."
---
```

## Supported proxies and providers

Any authenticating proxy that integrates with your identity provider over OIDC or SAML is compatible. Commonly used options include:

| Proxy / gateway | Integrates with | Notes |
| --- | --- | --- |
| [Cloudflare Access](https://developers.cloudflare.com/cloudflare-one/policies/access/) (Zero Trust) | Okta, Microsoft Entra ID, Google Workspace, SAML/OIDC | Managed service; no proxy to operate |
| [oauth2-proxy](https://oauth2-proxy.github.io/oauth2-proxy/) | Any OIDC provider | Open source; deployed alongside Evidence |
| [Pomerium](https://www.pomerium.com/) | OIDC and SAML providers | Open-source identity-aware proxy with group-based policy |
| [Authelia](https://www.authelia.com/) / [Authentik](https://goauthentik.io/) | Self-hosted identity store | No external provider required |
| AWS [Application Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html) | Amazon Cognito or any OIDC provider | Native authentication at the load balancer |
| Google Cloud [Identity-Aware Proxy](https://cloud.google.com/iap) | Google Workspace / Cloud Identity | Wraps the service; no proxy to operate |
| Azure [App Service authentication](https://learn.microsoft.com/azure/app-service/overview-authentication-authorization) | Microsoft Entra ID | Built-in authentication in front of the container |

These integrate with standard enterprise identity providers — including Okta, Microsoft Entra ID, Google Workspace, Auth0, Ping Identity, and OneLogin — over OIDC or SAML.
